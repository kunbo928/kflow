# 领域词

只在新词、重载词或相邻概念边界会改变行为、归属、公开契约或验收时使用。普通改动沿用已有单义词汇时跳过。

## 收敛

1. 先搜项目已有 glossary、领域文档、ADR、相邻代码、API、schema 与测试。已有定义优先；用户表达与它冲突时立即指出，不静默另造同义词。
2. 领域术语定义业务概念本身，不混入存储或框架细节。架构角色只说明本次责任与排除边界，不冒充长期领域词。
3. 仓库能唯一核实的事实由 Agent 查；产品含义、命名偏好或真实概念边界才问 owner。
4. 最小契约：canonical 名称、一两句定义、排除含义、一个能区分相邻概念的边界场景。
5. 用户陈述与代码不符时当场摊开：「代码整单取消，你刚说可以部分取消——以哪个为准？」
6. 术语一经钉死，写进项目已有 glossary 或当前 Work spec 的指针，不发明平行词典。没有归宿时请 owner 选，不默认创建 `CONTEXT.md`。

## 完成

每个会改变行为或验收的术语只有一个含义；实现、API、schema、文档与测试使用同一含义。一个不了解讨论过程的实现者能从定义和边界场景判断预期行为。

ADR 只在同时满足时才提议：难回退、缺少上下文会意外、源于真实取舍。
