# 诊断

核心不是把报错消掉，而是找到行为为什么偏离预期，并确认修完后偏离消失。诊断请求不等于修复授权：未获授权时不改产品代码或测试。

**根因是有效状态第一次变成无效状态的地方，不是报错点。** 修复只消除因果断点。

## 1. 先有能变红的环

没有覆盖用户症状的可重复信号，就不要进入假设。优先现成通道：失败测试、CLI / HTTP、浏览器、trace replay、好坏差分；必要时经用户确认做最小 harness。把环收紧：更快、判据单义、钉住时间与随机性、隔离文件系统和网络。

完成条件：已经跑过一次的**一条命令**，能在用户的精确症状上变红，可重复，秒级，Agent 能独立重跑。读代码编故事不能代替这条命令。建不出环就停止根因断言，列出已试通道和缺的权限或产物。

偶现问题追求更高复现率，不是一份完美复现。性能问题先建立可比较基线，再用 profiler / query plan，不用泛化日志猜慢点。

## 2. 复现并最小化

确认环打中的是用户描述的故障。red 之后每次删一个输入、调用方、配置、数据或步骤；删掉任一剩余元素都会转 green 时，最小化完成。原始完整场景与最小场景都保留可重跑指针。

## 3. 假设

测试前写出 3–5 个排序的可证伪假设：「若根因是 X，改变 Y 应使症状消失 / 改变 Z 应使症状加重。」说不出预测的丢掉。一次只动一个变量。

## 4. 探针

探针只放在能区分假设的边界。优先 debugger / REPL，其次定向日志。临时日志用唯一 `[DEBUG-{id}]` 前缀，收尾用一次搜索证明已移除。

## 5. 修复（仅授权后）

有正确接缝才把最小复现写成回归测试：先看它红，再修，再绿，再跑原始完整场景。接缝过浅会伪造保障；没有正确接缝本身就是发现，写入 Work，不硬塞测试。

修完：原始环不再红；去掉 `[DEBUG-…]`；扔掉一次性 harness。连续两三次假设被推翻时先重读路径与归属，不叠特殊分支。
