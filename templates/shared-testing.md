# 测试口径

测试不是可选项，AI 不能用“手工验证”“肉眼确认”替代可重复证据。本文件给分档口径，不做一刀切。

## 分档要求

| 技能 | 最低要求 |
|---|---|
| `k-feat-impl` | 按行为约束做 TDD；关键用户路径要有集成 / 端到端证据 |
| `k-issue-fix` | 先写复现测试红，再修到绿；影响面要有回归证据 |
| `k-refactor` | 先确认已有覆盖；不足则补刻画测试，再重构 |
| `k-feat-ff` | 不要求先写测试，但结束时必须有运行时测试通过 |
| `k-refactor-ff` | 默认只接已有测试能自证的小重构；没有可用测试就退完整 `k-refactor` |

## 证据层级

从强到弱：

1. 端到端 / 浏览器 / 调用方主路径测试
2. 集成测试（真实项目边界，不 mock 掉被验证对象）
3. 单元 / 组件测试
4. 类型检查 / lint

类型检查只能证明编译期约束，不能证明行为正确。

## 什么时候强制集成测试

出现任一情况时必须有集成或端到端证据：

- 用户可见主路径变化
- 跨模块编排变化
- 数据持久化 / 迁移 / 外部接口变化
- bug 的复现路径本来就是集成路径
- refactor 触及公开接口或多个调用方

纯内部局部逻辑变化可用单元测试覆盖；不要用 jsdom / mock 脚本冒充用户主路径验收。

## 不允许

- 只写“手工验证过了”
- 只跑类型检查就宣告行为正确
- 没有复现测试就修 bug
- 没有覆盖就做行为不变重构
- 因“太简单”跳过测试
