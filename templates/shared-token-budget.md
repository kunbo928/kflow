# Token 预算与读取分级

本文件由 `k-onboard` 复制到项目的 `.kflow/reference/`。目标是在不牺牲正确性的前提下降低长会话 token 消耗。

## 默认原则

- **先索引后正文**：先看目录名、frontmatter、标题、摘要、清单状态，再决定读哪一节。
- **先检索后打开**：`compound/`、历史 feature、roadmap、architecture 都先用文件名 / `search-yaml.py` / `rg` 缩小候选。
- **先相关节后全文**：只读当前阶段需要验证的章节；发现跨节矛盾、缺字段、要改写整篇时才读全文。
- **先摘要后证据**：输出给用户时先给结论和命中文件，细节只展开阻塞项、风险项、用户要 review 的正文。
- **一次只升级一个维度**：范围不清时先收窄目标，不同时扩大代码范围、文档范围和历史沉淀范围。

## 读取层级

| 层级 | 读取内容 | 什么时候用 |
|---|---|---|
| L0 索引 | 文件名、目录名、frontmatter、标题、状态字段 | 路由、续作、查重、判断是否存在 |
| L1 摘要 | summary、目录、相关清单项、命中行上下文 | 初步判断相关性、给用户候选 |
| L2 相关节 | 指定章节、命中段落、对应代码函数 | 设计 / 实现 / 验收的常规工作 |
| L3 全文 | 整份 doc 或完整 diff | 准备整体改写、做最终一致性检查、L2 证据冲突 |

默认从 L0/L1 开始。技能里写“读相关 doc”时按这个表执行；只有明确写“全文必读”或触发 L3 条件才读全文。

## 升级到全文的条件

- 要覆盖 / 重写这份文档。
- frontmatter、摘要、标题不足以判断状态或归属。
- 相关节之间出现矛盾，需要全局自洽检查。
- 用户要求完整审计、完整报告、全文 review。
- 验收 / 架构归并要修改目标 doc，且修改位置不明确。

## 搜索结果处理

- `compound/` 搜索默认只读命中的 1-3 份；命中更多时先按 `doc_type`、`status`、日期和关键词相关性排序。
- 历史 feature / issue 默认只读 frontmatter + summary + 相关节；不要批量打开完整历史正文。
- 架构文档先读 `ARCHITECTURE.md` 索引，再读相关子文档；不因为目录存在就全读。
- 代码先用 `rg` / imports / 文件名定位，避免从目录根递归阅读。

## 输出节制

- 阶段中间汇报只说：当前结论、证据位置、阻塞问题、下一步。
- 完整模板只在落盘文档里展开；聊天里给摘要 + 文件路径，除非用户要求贴全文。
- 发现多个候选时先列 3-5 个最高相关项，请用户缩范围；不要把长清单当进展。
